# Coding Standards & Development Workflow
## مجمع الشفاء الطبي ومسجد المدينة المنورة
---

# 1. الغرض من الوثيقة

تحدد هذه الوثيقة المنهجية الإلزامية التي يجب اتباعها عند تنفيذ أي مهمة برمجية داخل المشروع.

الأهداف:
- تقليل الأخطاء والتعديلات العشوائية.
- الحفاظ على المعمارية المعتمدة.
- منع التوسع غير الضروري.
- ضمان جودة الكود وقابليته للصيانة.
- التأكد من صحة النتائج بالاختبارات.
- حماية البيانات والمحتوى والصور.
- جعل كل تغيير قابلًا للفهم والمراجعة والتراجع.


لا يجوز تجاوز المنهجية لمجرد أن المهمة تبدو بسيطة، لكن يمكن اختصار الخطوات غير المنطبقة مع توثيق سبب الاختصار عند الحاجة.

# 2. المرجعية وترتيب الأولويات

ترتيب المرجعيات:

1. متطلبات الأمان وحماية البيانات.
2. وثيقة نطاق المشروع وقراراته المعتمدة.
3. التصميمات المعتمدة.
4. هذه الوثيقة.
5. وثائق المعمارية وعقود API.
6. متطلبات المهمة الحالية.
7. تفضيلات التنفيذ المحلية.

عند التعارض:
- لا يخترع الوكيل قرارًا معماريًا.
- يحدد التعارض بوضوح.
- يقترح أقل تغيير ممكن.
- يطلب قرارًا بشريًا إذا كان التعارض مؤثرًا.

يجب ألا يغيّر الوكيل نطاق المشروع أو الـ Tech Stack أو العقود المعتمدة ضمنيًا.

# 3. المبادئ الهندسية

## 3.1 Understand Before Modify
لا تعدّل ملفًا قبل فهم:
- دوره.
- مستهلكيه.
- اعتمادياته.
- الاختبارات المتعلقة به.
- أثر تغييره على بقية النظام.

## 3.2 Smallest Correct Change
نفذ أصغر تغيير يحقق متطلبات المهمة بالكامل.

لا تضف:
- Abstractions غير ضرورية.
- Design Patterns لمجرد استخدامها.
- مكتبات جديدة دون حاجة.
- طبقات إضافية دون مبرر.
- خصائص خارج نطاق المهمة.

## 3.3 Explicit Contracts
كل حد بين جزأين من النظام يجب أن يكون واضحًا.

يشمل ذلك:
- API Contracts.
- Database Models.
- Shared Types.
- Media References.
- Authentication.
- Error Responses.

## 3.4 Secure by Default
كل مدخل خارجي غير موثوق.

يشمل:
- Request Body.
- Query Parameters.
- Route Parameters.
- ملفات الصور.
- محتوى الأخبار.
- بيانات قاعدة البيانات المسترجعة.
- أي قيم قادمة من المتصفح.

يجب التحقق منها قبل استخدامها.

## 3.5 Verify, Don't Assume
لا يدعي الوكيل نجاح شيء لم يختبره.

يجب التمييز بين:
- تم التنفيذ.
- تم الاختبار ونجح.
- تم التنفيذ ولم يُختبر.
- الاختبار تعذر تشغيله.
- الاختبار فشل.

# 4. دورة تنفيذ المهام

كل مهمة تمر بالدورة التالية:

1. Read Context.
2. Inspect Existing Code.
3. Define Scope.
4. Create Implementation Plan.
5. Define Acceptance Criteria.
6. Implement.
7. Run Checks.
8. Review Changes.
9. Report Results.

لا يبدأ الوكيل التنفيذ قبل فهم النطاق والاعتماديات.

## المرحلة 1: Read Context

اقرأ:
- تعليمات المستودع.
- وثيقة تطوير المشروع.
- وثائق المعمارية ذات الصلة.
- عقود API ذات الصلة.
- وثائق قاعدة البيانات.
- تصميمات الواجهة المرتبطة بالمهمة.
- أي قرارات سابقة مرتبطة مباشرة بالمهمة.

لا حاجة لإعادة قراءة كل ملفات المستودع في كل مهمة.

## المرحلة 2: Inspect Existing Code

افحص:
- الملفات المتأثرة.
- الاستدعاءات المرتبطة.
- الاختبارات الحالية.
- المكتبات المستخدمة.
- نمط كتابة الكود القائم.
- حالة Git.
- أي تغييرات غير محفوظة تخص المستخدم.

لا تستبدل ملفًا قائمًا بالكامل لمجرد سهولة إعادة كتابته.

## المرحلة 3: Define Scope

حدد:

**Goal:** ما النتيجة المطلوبة؟

**In Scope:** ما الذي ستعدله المهمة؟

**Out of Scope:** ما الذي لن تعدله؟

**Dependencies:** ما الذي تعتمد عليه المهمة؟

**Acceptance Criteria:** ما الذي يثبت اكتمال المهمة؟

إذا كانت المهمة واضحة ومحدودة، لا تطلب موافقة إضافية على خطة روتينية.

إذا ظهر قرار معماري أو أمني مؤثر، توقف عند نقطة القرار.

## المرحلة 4: Implementation Plan

اكتب خطة قصيرة ومرتبة.

لكل خطوة:
- الملفات المتوقعة.
- التغيير المقصود.
- سبب التغيير.
- الاختبار المقابل.

يجب أن تكون الخطة محدودة بما يكفي لتنفيذها ومراجعتها.

لا تُنشئ ملفات أو وحدات مستقبلية لمجرد احتمال الاحتياج إليها.

## المرحلة 5: Implementation

نفذ خطوة بخطوة.

بعد كل مجموعة تغييرات منطقية:
- افحص Diff.
- تحقق من عدم إدخال تغييرات غير مقصودة.
- شغّل فحصًا مناسبًا مبكرًا.
- تابع إلى الخطوة التالية.

لا تنتظر نهاية المهمة لاكتشاف أخطاء TypeScript أو أخطاء البناء الأساسية.

## المرحلة 6: Verification

شغّل الاختبارات المناسبة للمهمة.

الحد الأدنى المعتاد:
- TypeScript Check.
- Lint.
- Tests.
- Build عند الحاجة أو قبل إتمام المهمة.

أضف اختبارات خاصة بالمخاطر أو قواعد العمل.

لا تتجاوز اختبارًا فاشلًا عن طريق حذفه أو تعطيله دون مبرر واعتماد مناسب.

## المرحلة 7: Review

راجع:
- صحة منطق التنفيذ.
- الأمان.
- توافق API.
- تأثير التغيير على البيانات.
- معالجة الأخطاء.
- Accessibility.
- SEO إذا تأثر الموقع العام.
- الأداء إذا تأثرت مسارات حرجة.
- عدم إدخال Dependency غير مبررة.
- عدم وجود Debug Code أو أسرار.

## المرحلة 8: Final Report

قدم تقريرًا يحتوي على:

1. ما تم تنفيذه.
2. الملفات الرئيسية التي تغيرت.
3. القرارات المتخذة.
4. الاختبارات التي شُغلت ونتائجها.
5. أي اختبارات لم تُشغل وسبب ذلك.
6. المخاطر أو الأعمال المتبقية.
7. خطوات التشغيل أو المراجعة إن لزم.

لا تقل إن المهمة مكتملة إذا كانت معايير قبولها لم تتحقق.


## ترتيب التنفيذ

1. تأسيس البنية.
2. البنية التحتية للسيرفر.
3. المصادقة.
6. إدارة المحتوى.
4. الموقع العام SSR.
5. مكتبة الصور.
7. واجهات الإدارة.
8. الربط والتكامل.
9. اختبارات الإطلاق.
10. النشر والتشغيل.

يمكن تعديل الترتيب حسب الاعتماديات، لا حسب سهولة المهمة فقط.

# 6. Coding Standards

## 6.1 TypeScript

- استخدام TypeScript في التطبيقات الأساسية.
- تفعيل Strict Mode.
- تجنب any.
- عدم استخدام Type Assertions لتجاوز مشكلة غير مفهومة.
- استخدام unknown عند التعامل مع بيانات غير موثوقة.
- التحقق من البيانات عند حدود النظام.
- عدم اعتبار TypeScript Runtime Validation.
- عدم تكرار أنواع العقود بين التطبيقات دون مصدر مشترك واضح.

تُستخدم أنواع العقود المشتركة للبيانات التي تتبادلها التطبيقات.

لا تُشارك:
- أسرار السيرفر.
- Database Documents الداخلية دون حاجة.
- تفاصيل الجلسات.
- تفاصيل التنفيذ الخاصة بالـ Backend.

## 6.2 Naming

- أسماء واضحة تعبّر عن الوظيفة.
- الالتزام بنمط تسمية ثابت.
- عدم استخدام اختصارات غامضة.
- تسمية دوال التحقق والتحويل وفق دورها.
- التمييز بين API DTO وDatabase Model عند اختلاف المسؤولية.

## 6.3 Functions

يفضل أن تكون الدوال:
- محددة المسؤولية.
- ذات مدخلات ومخرجات واضحة.
- قليلة الآثار الجانبية.
- سهلة الاختبار.

لا تُقسم كل دالة إلى عدة دوال صغيرة دون قيمة فعلية.

## 6.4 Error Handling

- استخدام أخطاء واضحة ومصنفة.
- عدم إرجاع Stack Traces للعميل.
- عدم ابتلاع الأخطاء بصمت.
- تسجيل الأخطاء التشغيلية بصورة آمنة.
- عدم تسجيل كلمات المرور أو بيانات الجلسات.
- تقديم رسائل مناسبة للمستخدم.
- الحفاظ على التفاصيل التقنية في السجلات الموثوقة.

## 6.5 Dependencies

قبل إضافة أي مكتبة:
1. تحقق من إمكانية الحل بالأدوات الحالية.
2. تحقق من توافق المكتبة.
3. راجع الصيانة والمخاطر.
4. راجع حجمها وأثرها على الأداء.


## 6.6 Comments

تُكتب التعليقات لتفسير:
- لماذا اختير الحل.
- القيود.
- السلوك غير البديهي.
- المخاطر أو الـ Workarounds.

لا تكتب تعليقات تعيد صياغة الكود حرفيًا.


# 7. Backend Architecture

يعتمد السيرفر فصلًا واضحًا للمسؤوليات دون فرض طبقات زائدة.

التدفق المقترح:

HTTP Request
→ Route
→ Middleware
→ Controller
→ Service
→ Data Access
→ MongoDB

ليس مطلوبًا إنشاء جميع الطبقات لكل Endpoint إذا لم تضف قيمة.



# 8. MongoDB Standards

- تحديد Schema لكل Collection.
- إنشاء الفهارس بناءً على الاستعلامات الحقيقية.
- تجنب الفهارس غير الضرورية.
- تحديد قواعد Unique عند الحاجة.
- التحقق من المعرفات قبل الاستعلام.
- استخدام Pagination مستقرة.
- عدم الاعتماد على ترتيب غير محدد.
- منع التحديثات الجماعية غير المقصودة.
- عدم استخدام بيانات العميل مباشرة كـ Query Object.

# 10. Content Publishing Rules

المحتوى له حالتان:
- Published.
- Hidden.

لا توجد مسودات ضمن النطاق الحالي.

كل استعلام عام يجب أن يفرض شرط النشر في طبقة موثوقة من السيرفر.

لا يُعتمد على إخفاء العناصر في الواجهة فقط.

يجب اختبار:
- القوائم العامة.
- تفاصيل المحتوى.
- البحث.
- Sitemap.
- Metadata.
- الصفحات المخزنة مؤقتًا.

عند إخفاء المحتوى:
- يمنع الوصول العام إليه وفق السياسة المعتمدة.
- تُراجع Cache Invalidation.
- يُزال من Sitemap.
- تُمنع تسريباته عبر API أو HTML SSR.

# 12. React Standards

- Components ذات مسؤوليات واضحة.
- فصل منطق API عن Presentation عند الحاجة.
- استخدام Forms قابلة للوصول.
- إدارة حالات Loading وEmpty وError وSuccess.
- منع تكرار الطلبات غير الضروري.
- التعامل مع أخطاء الشبكة.
- عدم وضع الأسرار داخل Frontend.
- عدم تكرار Business Logic بين الأدمن والسيرفر.
- عدم بناء Generic Components معقدة قبل وجود احتياج متكرر فعلي.

## SSR

- عدم استخدام Browser APIs أثناء تنفيذ السيرفر.
- تجنب اختلاف HTML بين السيرفر والمتصفح.
- استخدام بيانات أولية متوافقة مع SSR.
- اختبار Hydration.
- معالجة أخطاء Rendering.
- فصل مسارات الموقع العام عن ملفات الأدمن.
- استخدام Escape آمن للمحتوى.
- منع إدخال HTML غير موثوق دون Sanitization مدروس.

# 13. SEO Standards

عند تعديل صفحة عامة، يجب مراجعة:

- SSR Output.
- Title.
- Description.
- Canonical.
- Open Graph.
- Heading Structure.
- Internal Links.
- Status Codes.
- Sitemap.
- Robots.
- Structured Data عند الحاجة.

لا يُستخدم noindex كحل عام لإخفاء محتوى سري؛ الحماية يجب أن تكون من السيرفر.

يجب منع فهرسة صفحات الإدارة.

لا يُسمح بتوليد Metadata من محتوى غير موثوق دون معالجة مناسبة.

أي صفحة جديدة قابلة للفهرسة تحتاج اختبارًا واضحًا.

# 14. Accessibility Standards

كل مكون جديد أو معدل يجب أن يراعي:

- Semantic HTML.
- Keyboard Navigation.
- Visible Focus.
- Accessible Names.
- Form Labels.
- Error Association.
- Color Contrast.
- RTL.
- Focus Management.
- Responsive Reflow.
- Reduced Motion.
- Screen Reader Behavior.

لا تستخدم div كزر أو رابط دون سبب تقني حقيقي.

لا تُستخدم ARIA بديلًا عن HTML الدلالي عندما يكون العنصر الأصلي مناسبًا.

يجب أن يكون لكل Dialog:
- اسم مفهوم.
- Focus مناسب عند الفتح.
- إمكانية إغلاق واضحة.
- معالجة صحيحة للتركيز عند الإغلاق.

# 15. Design System Standards

- استخدام Tokens المشتركة.
- عدم تكرار الألوان الأساسية.
- عدم وضع قيم الهوية داخل مكونات منفصلة.
- استخدام Tailwind CSS v4.
- عدم تعديل الهوية البصرية ضمن مهمة وظيفية دون طلب.
- الحفاظ على التصميمات المعتمدة.
- اختبار Responsive Layout.
- مراعاة RTL.

عند تعديل global.css:
- فحص أثر التعديل على التطبيقين.
- تشغيل Build للتطبيقين.
- مراجعة الواجهات المتأثرة.

يُسمح بالأنماط المحلية للمكونات عندما تكون خاصة بها فعلًا.

# 21. Definition of Done

لا تُعتبر المهمة مكتملة إلا عند تحقق:

1. تحقيق متطلبات المهمة.
2. استيفاء معايير القبول.
3. توافق التغيير مع المعمارية.
4. نجاح الاختبارات المطلوبة.
5. مراجعة Diff.
6. عدم وجود أسرار أو بيانات حساسة في الكود.
7. تحديث الوثائق المتأثرة.
8. معالجة الأخطاء المعروفة.
9. تقديم تقرير دقيق.

إذا كانت هناك خطوة ناقصة، توصف المهمة بأنها Partially Complete أو Blocked أو Implemented but Unverified بحسب الحالة.

# 22. تعليمات إلزامية لوكيل البرمجة

- اقرأ التعليمات قبل التنفيذ.
- افهم الكود الحالي قبل تغييره.
- لا تفترض وجود ملفات أو Scripts غير مفحوصة.
- لا تنشئ بدائل لملفات موجودة دون داعٍ.
- لا تغير نطاق المهمة.
- لا تخفِ الأخطاء.
- لا تتجاوز الاختبارات بتعطيلها.
- لا تحذف بيانات.
- لا تعدل أسرار الإنتاج.
- لا تنفذ نشرًا إنتاجيًا أو عمليات غير قابلة للعكس دون موافقة.
- لا تعتبر Build ناجحًا دليلًا على صحة منطق العمل.
- لا تكتب ملفات توثيقية لمجرد زيادة العدد.
- لا تكرر الكود لتجنب فهم abstraction قائم.
- لا تبالغ في التجريد.
- لا تنهِ المهمة دون تقرير.

# 26. اعتماد الوثيقة

هذه الوثيقة هي المرجع المقترح لمنهجية تنفيذ المشروع.

قبل اعتمادها نهائيًا، تُربط بالتالي:
- وثيقة تطوير الموقع.
- وثيقة المعمارية.
- عقود API.
- سياسة إدارة المحتوى.
- إعدادات المستودع.
- CI Checks.
- ملفات تعليمات وكيل البرمجة.

بعد الاعتماد، يبدأ التنفيذ بمهمة تأسيس المشروع وفق هذه المنهجية.
