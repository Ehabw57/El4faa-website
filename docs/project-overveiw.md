**نوع المشروع:** موقع توثيقي خيري + لوحة إدارة محتوى

# 1. الهدف من المشروع

بناء موقع عربي احترافي لتوثيق مشروع مجمع الشفاء الطبي ومسجد المدينة المنورة، وعرض مراحله واحتياجاته وأخباره وصوره، وإتاحة التواصل المباشر مع الجهة المسؤولة لمن يرغب في المساهمة.

يهدف الموقع إلى:
- تعريف الزوار بالمشروع وأهدافه.
- عرض مراحل التنفيذ ومعلوماتها وصورها.
- توضيح الاحتياجات الحالية للمشروع.
- نشر الأخبار والتحديثات.
- إتاحة وسيلة واضحة للتواصل.
- تمكين مسؤول واحد من إدارة المحتوى بسهولة.
- تحسين قابلية اكتشاف صفحات الموقع بمحركات البحث.
- توفير تجربة عربية RTL ميسرة وسريعة على الهاتف والحاسوب.

# 3. بنية التطبيقات

Monorepo واحد يحتوي على تطبيقين تطبيقيين.

## التطبيق الأول: Server + Public Website

المسؤوليات:
1. تشغيل Express.js.
2. تقديم REST API.
3. تقديم الموقع العام باستخدام React SSR.
4. إدارة المصادقة والجلسات.
5. التحقق من المدخلات.
6. تطبيق قواعد العمل.
7. التعامل مع MongoDB.
8. التعامل الآمن مع Cloudinary.
9. تقديم صفحات الأخطاء ومعالجة الاستثناءات.
10. توفير سجلات تشغيل مناسبة.

يُبنى الموقع العام باستخدام React وTypeScript، مع تنفيذ SSR صريح.

Express مسؤول عن:
- مسارات API.
- مسارات الموقع العام.
- توجيه الطلبات إلى طبقة SSR.
- تقديم الأصول الثابتة عند الحاجة.
- إدارة Middleware.
- معالجة الأخطاء.

يجب ألا يؤدي تعطل JavaScript في المتصفح إلى اختفاء المحتوى الأساسي الذي تم عرضه من السيرفر، قدر الإمكان.

## التطبيق الثاني: Admin Dashboard

التقنيات:
- React.
- TypeScript.
- Vite.
- Tailwind CSS v4.

المسؤوليات:
- واجهة تسجيل الدخول.
- لوحة الملخص.
- إدارة الاحتياجات.
- إدارة مراحل التنفيذ.
- إدارة الأخبار والتحديثات.
- مكتبة الصور.
- تسجيل الخروج.
- حالات التحميل والأخطاء والنجاح.
- التواصل مع REST API.

الأدمن SPA مستقلة، ولا يحتوي على Backend أو قاعدة بيانات خاصة به.

يستخدم نفس API الذي يستخدمه الموقع العام، مع اختلاف صلاحيات الوصول.

هذا الملف هو المصدر المركزي للقيم البصرية المستخدمة في التطبيقين.

يشمل:
- ألوان الهوية.
- ألوان النصوص والخلفيات.
- الخطوط.
- الأحجام الطباعية.
- المساحات.

- الحدود.

- Tokens الخاصة بالحالات.
- قواعد RTL الأساسية المناسبة.

يُستخدم Tailwind CSS v4 في التطبيقين.

لا تُكرر قيم الألوان والمساحات والخطوط في ملفات مستقلة داخل كل تطبيق دون ضرورة موثقة.

# 9. قواعد إدارة المحتوى

حالات المحتوى:
- منشور.
- مخفي.

لا توجد حالة مسودة ضمن نموذج العمل الحالي.

النشر مباشر عند الحفظ كمنشور.

المحتوى المخفي:
- يبقى متاحًا للمسؤول.
- لا يظهر في الصفحات العامة.
- لا يظهر في نتائج البحث العامة أو الـ Sitemap.
- يمكن إظهاره مجددًا.

تتطلب عملية الإخفاء تأكيدًا واضحًا.

تُعامل كل عملية حذف نهائي بشكل منفصل عن الإخفاء.

يجب التمييز بين حذف المحتوى وحذف ملف الصورة الأصلي.

# 10. مكتبة الصور وقواعد الملكية

لكل صورة:
- معرف داخلي.
- معرف الأصل في Cloudinary.
- رابط التسليم أو العرض.
- بيانات الملف.
- الأبعاد عند توفرها.
- النص البديل عند الحاجة.
- تاريخ الرفع.
- علاقات الاستخدام.

يجب الاحتفاظ بمعرف ثابت للأصل في Cloudinary، وعدم الاعتماد على الرابط وحده كهوية للصورة.

## إعادة الاستخدام
عند اختيار صورة موجودة:
- يُنشأ ارتباط جديد بالمحتوى.
- لا يُرفع الملف مرة أخرى.
- لا يُنشأ أصل مكرر.

## إزالة الارتباط
إزالة صورة من خبر أو مرحلة أو احتياج:
- تزيل العلاقة فقط.
- لا تحذف الأصل.

## الحذف النهائي
يجب:
- إظهار المحتوى المرتبط بالصورة.
- منع الحذف غير الآمن.
- طلب تأكيد صريح.
- التحقق من عدم وجود علاقات فعالة قبل الحذف.
- التعامل مع فشل Cloudinary أو قاعدة البيانات بطريقة قابلة للاسترداد.

لا نعتمد على الحذف المتزامن غير المحمي بين MongoDB وCloudinary كأنه عملية ذرية واحدة.

تُنفذ سياسة حذف آمنة باستخدام حالات داخلية وإعادة محاولة أو إجراء تعويضي عند الحاجة.

رفع الصورة وحده لا يجعلها منشورة على الموقع العام.

- DELETE /api/admin/media/:id

تُضاف مسارات تغيير حالة النشر والإخفاء إذا كان ذلك أنسب لعقد API المعتمد.

يمكن دمج أو تغيير المسارات حسب تصميم العقود، بشرط الحفاظ على وضوح المسؤوليات وعدم التكرار.

توثيق API يجب أن يشمل:
- المدخلات.
- المخرجات.
- الأخطاء.
- التحقق من الصلاحيات.
- قواعد pagination.
